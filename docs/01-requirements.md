# 1. Требования (v0.2)

Статус: **утверждена пользователем 2026-09-30**, кроме вопросов автору кейса (п. 13, полный список в `questions-for-author.md`). Проектирование идёт на временных допущениях.
Изменения относительно v0.1: в скоуп вошли авторизация и роли, уведомления, статистика; введены глоссарий, матрица прав, жизненный цикл брони, трассируемость.

## 1. Цель и границы

Прототип системы бронирования переговорных комнат: просмотр комнат, создание, изменение и отмена броней, календарь занятости, поиск свободных комнат, уведомления, статистика использования.
Инвариант: **в одной комнате нет двух активных броней с пересекающимися интервалами**.

**В скоупе:** вход по email и паролю, роли, справочники (пользователи, комнаты, оборудование), брони, календарь во фронтенде, поиск, уведомления в приложении, статистика, экспорт статистики в CSV.

**Вне скоупа:** повторяющиеся встречи, email и Telegram-уведомления, интеграция с внешними календарями (.ics), самостоятельная регистрация, сброс пароля по почте, drag-and-drop броней, история изменений брони, мобильное приложение.

## 2. Заинтересованные стороны

| Сторона | Интерес |
|---|---|
| Сотрудник | Быстро найти и занять комнату без конфликтов |
| Администратор | Управлять справочниками и пользователями, видеть использование ресурсов |
| Автор кейса / проверяющий | Работающий прототип, корректная логика пересечений, документация |
| Разработчик | Ограниченный объём, проверяемые критерии |

## 3. Глоссарий

| Термин | Значение |
|---|---|
| Бронь | Запись «комната + интервал + организатор + тема» |
| Организатор | Пользователь, создавший бронь |
| Активная бронь | Бронь со статусом `active`; только она блокирует слот |
| Слот | Интервал времени в конкретной комнате |
| Пересечение | Два интервала одной комнаты, у которых `a.start < b.end` и `b.start < a.end` |
| Рабочие часы | 08:00–20:00 по локальному времени организации |
| Загрузка комнаты | Занятые минуты рабочих часов ÷ доступные минуты рабочих часов за период |

## 5. Жизненный цикл брони

```
        создание            отмена (организатор/админ)
(нет) ───────────► active ───────────────────────────► cancelled
                     │  ▲
                     └──┘ изменение (повторная проверка пересечений)
```

- Статусов два: `active` и `cancelled`. «Прошедшая» и «идёт сейчас» вычисляются по времени и не хранятся.
- `cancelled` — конечное состояние, вернуть нельзя (создаётся новая бронь).
- Запись после отмены сохраняется для статистики.

## 8. Бизнес-правила

| ID | Правило |
|---|---|
| BR-1 | Начало строго раньше конца |
| BR-2 | Бронь в прошлом создать нельзя (начало не раньше текущего момента, округлённого до шага) |
| BR-3 | Начавшуюся бронь можно только сократить (уменьшить конец) или отменить; закончившуюся — нельзя менять и отменять |
| BR-4 | Длительность от 15 минут до 8 часов; начало и конец кратны 15 минутам |
| BR-5 | Бронь целиком внутри рабочих часов 08:00–20:00 и в пределах одних суток |
| BR-6 | Число участников от 1 до вместимости комнаты |
| BR-7 | Отключённую комнату забронировать нельзя; существующие брони в ней остаются |
| BR-8 | Отменённая бронь не участвует в проверке пересечений |
| BR-9 | Интервалы полуоткрытые `[start, end)`: 10:00–11:00 и 11:00–12:00 не пересекаются |
| BR-10 | Заблокированный пользователь не входит; его предстоящие брони остаются, администратор может их отменить |
| BR-11 | Напоминание создаётся только для активных броней, начало которых в будущем; при переносе брони напоминание пересчитывается, при отмене — не отправляется |
| BR-12 | Уведомление об изменении или отмене не создаётся, если действие выполнил сам организатор |
| BR-13 | Администратор не может заблокировать или разжаловать самого себя (защита от потери доступа) |

## 9. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-1 | Целостность | Пересечения невозможны даже при параллельных запросах; гарантия на уровне БД |
| NFR-2 | Время | Хранение в UTC (`timestamptz`), API — ISO 8601 с offset, UI — локальная зона организации из конфига |
| NFR-3 | Безопасность | Пароли только в виде хеша (argon2 или bcrypt); токены с ограниченным сроком; проверка прав на бэкенде для каждого запроса |
| NFR-4 | Безопасность | Защита от подбора пароля: ограничение частоты попыток входа |
| NFR-5 | Производительность | Типичные операции < 300 мс при ~50 комнатах, ~50 000 броней, ~500 пользователей |
| NFR-6 | Надёжность | Фоновая задача напоминаний переживает перезапуск сервиса и не дублирует уведомления |
| NFR-7 | Развёртывание | Запуск с нуля одной командой (`docker compose up`), миграции и сид применяются автоматически |
| NFR-8 | Тестируемость | Автотесты покрывают правила пересечений, границы интервалов, права и гонки |
| NFR-9 | Валидация | Все правила проверяются на бэкенде; фронтенд только подсказывает |
| NFR-10 | Интерфейс | Русский язык, актуальные Chrome и Firefox, читаемость от 360 px, доступность с клавиатуры для форм |
| NFR-11 | Сопровождаемость | Типы фронтенда генерируются из OpenAPI; изменение контракта ломает сборку |

## 10. Сущности (концептуально)

| Сущность | Ключевые поля |
|---|---|
| Пользователь | id, ФИО, email (уникален), хеш пароля, роль (`employee`/`admin`), активен |
| Комната | id, название, местоположение (текст, необязательно), вместимость, описание, активна |
| Оборудование | id, название; связь «многие ко многим» с комнатой |
| Бронь | id, комната, организатор, тема, начало, конец, участники, статус, создана, изменена |
| Уведомление | id, получатель, тип (`reminder`/`changed`/`cancelled`), бронь, текст, создано, прочитано |

Структура помещений (здания и этажи) не смоделирована отдельно, пока не уточнено у автора кейса (п. 13). Поле «местоположение» оставляет возможность вынести её в сущности позже.
